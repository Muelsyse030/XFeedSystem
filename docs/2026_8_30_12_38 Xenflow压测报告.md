# Xenflow 压力测试报告

**报告日期**：2026-08-30
**测试对象**：Xenflow 内容社区（Go + Gin + MySQL + Redis + Meilisearch）

---

## 1. 测试目标

1. 摸清新服务器（8 核 / 15G，测试机 1.15.73.178）在模拟社区负载下的吞吐与延迟拐点；
2. 与旧服务器（2 核 / 1.6G，生产机 139.196.126.52）对比；
3. 用 pprof 定位 CPU 热点，给出可执行的优化建议；
4. 主服务器与域名（xenflow.cyou）保持不变，测试机仅作压测环境。

## 2. 测试环境

| 项目 | 旧服务器（生产） | 新服务器（测试） |
|---|---|---|
| CPU / 内存 | 2 vCPU / 1.6GB（无 swap） | 8 vCPU / 15GB |
| 磁盘 | 40G | 50G |
| 架构 | nginx → 2× Go API(8001/8002) + worker；Docker: MySQL/Redis/Meilisearch | 与旧机完全一致的复制（同版本、同数据） |
| 数据规模 | 用户 1033 · 帖子 612 · 评论 8648 · 主题 11 · 搜索索引 590 | 与旧机一致（复制后校验相同） |
| 压测入口 | https://xenflow.cyou/api（公网 TLS） | http://127.0.0.1/api（本地回环经 nginx，排除公网干扰） |

## 3. 测试方法与场景

### 3.1 场景（读 80% / 写 20%）

| 类型 | 接口 | 权重 |
|---|---|---|
| 读 | GET /feed、/notes/:id、/topics/hot、/topics/:id/feed、/search、/users/:id、/users/:id/notes | 80 |
| 写 | POST /notes/:id/like、favorite、comments、/users/:id/follow、/topics/:id/follow、/notes（发布） | 20 |

随机数据取自线上真实库（639 个有效笔记 ID、1000+ 用户 ID），写接口使用按生产 JWT 密钥铸造的测试令牌（50 个测试用户）。

### 3.2 负载模型

逐级加压：20 → 50 → 100 → 150 → 200 → 250 → 300 并发，每级 120 秒（warmup 60 秒）。

**熔断（自动停止）条件**（任一满足即停）：
- 错误率 ≥ 5%（客户端超时 / 5xx）
- p99 ≥ 1500ms
- 吞吐相对上一级回落 >10% 且 p95 恶化 >50%（判为“明显性能下降”）
- 级别内瞬时 p99 > 2000ms 立即中止

## 4. 压测结果

### 4.1 新服务器（8 核 / 15G，经 nginx 本地回环）

| 并发 | 请求数 | QPS | p50 | p95 | p99 | 最大 | 错误率 |
|---|---|---|---|---|---|---|---|
| 20（warmup） | 74,398 | **1,240** | 4ms | 90ms | 117ms | 261ms | 0% |
| 50 | 80,567 | 671 | 24ms | 348ms | 510ms | 938ms | 0% |

→ 50 并发时吞吐明显回落（1240 → 671 QPS）且延迟翻倍，触发熔断，测试停止。

> 另一次 20 并发复测（pprof 采样期间）：905 QPS，p50 2ms，p95 213ms，0% 错误。

### 4.2 旧服务器（2 核 / 1.6G，经公网 TLS）

| 并发 | QPS | p50 | p95 | p99 | 错误率 |
|---|---|---|---|---|---|
| 20 | ~104 | 88ms | 802ms | 1.07s | 0% |
| 50 | ~93 | 269ms | 2,102ms | 2.77s | 0% |

→ 旧机在 50 并发即出现 p99 > 2s 的严重劣化；压测期间曾触发整机假死（内存耗尽、无 swap、SSH 握手超时）。

### 4.3 对比与参考标准

| 指标 | 参考标准（混合场景） | 旧机 20 并发 | 新机 20 并发 |
|---|---|---|---|
| QPS | ~970 | ~104 | 1,240 |
| p50 | <60ms | 88ms | 4ms |

新机在 20 并发即超过参考标准约 1.3 倍（QPS），p50 远优于标准。50 并发时两者都出现明显劣化，但新机绝对性能仍约为旧机 7 倍。

## 5. pprof 瓶颈分析

测试机开启 `ENABLE_PPROF=1` 后，在 20 并发 / ~900 QPS 下对 API 实例采样 30 秒。

### CPU 热点（total samples 76.24s / 252.88%）

| 函数 | flat | cum |
|---|---|---|
| **XFeedSystem/internal/service.diverseRank（Feed 多样性排序）** | 20.55% | **82.86%** |
| runtime.mapaccess1_fast64（map 查找） | 25.21% | 60.20% |
| runtime/maps 内部（h2 / memhash64 / matchH2 等） | ~24% | ~24% |
| topicOverlap（inline） | 1.38% | 1.44% |

**结论**：Feed 列表的多样性排序算法 `diverseRank` 是绝对 CPU 瓶颈（占 82.86%）。该算法对候选集做 O(N²) 轮次遍历：每选出一条笔记，就对全部剩余候选做作者计数 map 查找、话题重叠判断和类型衰减，并改写分数。候选规模越大，map 哈希操作越密集（mapaccess1_fast64 占 60% 累计）。

### 堆分析（inuse_space 22.5MB）

| 函数 | cum |
|---|---|
| (*FeedService).getFeedPage | 46.24% |
| runtime.allocm / database/sql / MySQL 驱动 | ~25% |

Feed 页构建（getFeedPage）是主要内存分配来源，与 CPU 热点一致（每次 /feed 都重建候选与排名）。

**瓶颈链条**：/feed → getFeedPage → diverseRank（O(N²)、map 密集）→ 2 核/8 核 CPU 饱和 → 并发升高时吞吐下降、延迟飙升。

## 6. 结论

1. **新机器足以支撑当前社区**：20 并发 1,240 QPS、p50 4ms，已超过参考标准；日常千人社群负载（远低于 20 并发）无压力。
2. **系统真正的瓶颈是应用层算法，不是硬件**：`diverseRank` 的 O(N²) 实现占 CPU 82.9%，在 50 并发时就成为吞吐天花板（新机 671 QPS / 旧机 93 QPS 均受其限）。
3. 旧机另有资源短板：1.6G 无 swap，压测曾导致整机假死——不宜再作为承载目标。

## 7. 优化建议（按优先级）

1. **优化 diverseRank（收益最大）**：
   - 降低复杂度：用作者/话题计数代替每次全量衰减重算；或对候选预排序后做贪心选择；
   - 缓存排名结果（按时间窗/游标缓存 Feed 页），避免每个请求全量重排；
   - 限制参与排序的候选数（如取打分 Top 100 再做多样性）。
2. **API 运行模式**：生产切 release 模式（关闭 gin debug 每请求日志），减少日志开销。
3. **修复 worker 统计 SQL**（`reads` 保留字导致每条统计插入失败、空转 MySQL），消除后台干扰。
4. **资源层**：正式环境建议 4G+ 内存并配置 swap；MySQL 连接数按实际并发收敛。

## 8. 附注

- 压测在测试机产生少量测试互动数据（测试用户 90000-90049 的点赞/评论/关注），已可随时清理；生产数据未受影响。
- 测试机 nginx 监听 80 端口，公网访问需在腾讯云安全组放行。
- `ENABLE_PPROF=1` 仅配置在测试机，生产未开启。
- 迁移完整性已校验：用户/帖子/评论/主题数量与生产一致，Redis 1070 键一致，搜索索引 590 篇与库一致。
