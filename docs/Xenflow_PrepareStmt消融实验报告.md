# XFeedSystem GORM PrepareStmt 消融实验报告

**日期**：2026-09-01
**方法**：同一套代码，唯一变量 = `gorm.Config{PrepareStmt: true}`。基线在 101.43.11.57（无 PrepareStmt），消融在 110.40.137.114（有 PrepareStmt），均为 8 vCPU / 15G，数据同为 612 条笔记干净基线，负载同为 80/20 混合（13 接口，20-1000 并发 × 45s）。

**平均提升约 +14%**，吞吐平台从 ~4.7K QPS 抬升到 ~5.5K QPS，全部并发档 0% 错误。

## 二、机制分析

### CPU 剖面（300c）

| 指标 | 基线 | PrepareStmt |
|---|---:|---:|
| syscall.Syscall6 | 18.87% | 19.22% |
| mallocgc（cum） | 15.39% | 15.86% |
| scanobject | 6.56% | 6.46% |

CPU 形状基本不变（仍是 I/O + GC 主导），但 QPS 更高——说明**每请求更便宜**，提升来自 MySQL 端 SQL 解析/执行计划缓存，而不是 Go 侧算力。

### 分配剖面（500c，20s 窗口）

| 分配源 | 基线占比 | PrepareStmt 占比 |
|---|---:|---:|
| gorm AddVar | 12.6% | 9.9% |
| Statement.clone | 3.1% | 4.5% |
| reflect.New | 11.1% | 13.4% |
| Redis readStringReply | 8.8% | 9.7% |

**关键发现：Go 侧分配没有显著下降**。原因：系统大量查询是动态 IN 列表（`GetByIDs` 的 id 集合长度随请求变化），GORM 的预编译缓存按完整 SQL 字符串为 key，动态 SQL 缓存命中率低，语句构建（AddVar/clone）仍然发生。分配剖面的绝对量还因 QPS 提高而上升。

因此 PrepareStmt 的收益主要来自：
1. **固定形状查询**（用户查询、Feed 引擎重建、计数查询等）走真正的预编译；
2. **MySQL 端 SQL 解析/执行计划缓存**（服务端 prepared statement），省 CPU 与锁开销。

## 三、结论

**PrepareStmt 是低成本、无副作用的正收益优化（+8~18% QPS），值得保留。** 但它不是"分配优化"的银弹——由于动态 IN 查询，GORM 语句构建开销仍在。

对下一步方向的修正：
- **P1（PrepareStmt）已落地并验证**；
- **P0（互动路径减 DB 往返）依然是最大杠杆**：热点写 ~2.6K QPS 受限于每请求 3-4 次 DB 往返，与 PrepareStmt 正交；
- **P2（排名缓存 LIMIT 分页）优先级上升**：分配剖面里 Redis ZSET 全量读写（readStringReply 9.7% + ZSliceCmd + zAddArgs ≈ 15%）已成为与 GORM 并列的分配大头，且与动态 SQL 无关，改 LIMIT 分页直接可减；
- **搜索缓存**：占 CPU cum 16% 但流量只有 10%，独立可加。
