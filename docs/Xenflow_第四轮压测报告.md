# Xenflow 第四轮压测报告（计数器异步化验证）

**日期**：2026-09-01
**测试服务器**：122.51.117.19（8 vCPU / 15G，nginx → xfeed-api@1/2 + xfeed-worker）
**部署代码**：v5（含 Redis Counter + Counter Worker + Lua 原子 Drain + 批量落库）
**数据**：612 条笔记（590 发布）/ 1083 用户，真实热点笔记：**100140**（7.6 万赞，互动总量第一）、**100172**（8,646 条评论，评论第一；点赞数 7.6 万为导入假计数，真实关系表仅 80 行，反而适合制造真实写压力）
**压测方式**：混合 80/20（13 接口）+ 单热点 Like/Favorite/Comment（全部用户打同一笔记）+ 故障恢复 + 一致性校验，ID 全部取自真实库

---

## 一、第四轮关键结论

1. **热点行锁问题已解决**：互动事务里已无 `UPDATE notes SET counter+1`，行锁竞争消失。
2. **剩余错误根源是 MySQL 连接上限（151），不是行锁**：第一轮热点测试 200c 时 50% 错误全部是 `Error 1040: Too many connections`。
3. **把 max_connections 151 → 400 后，混合与热点场景 200/300/500 并发全部 0% 错误**。
4. **过程中发现并修复了计数器实现的 3 个 bug**（见 §四），修复后计数正确性完整验证：+500 点赞 → like_count +500，+300 收藏 → +300。
5. **新瓶颈浮现：事件管道吞吐**（relay 约 500 事件/秒），评论洪峰（3500 事件/秒）会造成积压和计数延迟，但最终一致、零丢失。

## 四、过程中发现并修复的 3 个 bug

1. **去重键前缀污染 Flusher**：`counter:dedup:{eventID}` 被 `SCAN counter:*` 误扫，30 万条评论事件产生 29 万个去重键，Flusher 每次被淹没。修复：去重键改为 `cntdedup:{eventID}`。
2. **BatchAddCounters CASE WHEN 语法错误**：WHEN 子句之间用逗号连接（`THEN 3,WHEN`），多笔记批量时 SQL 1064 报错，单笔记时恰好能过——所以手动验证通过、压测全挂。修复：去掉逗号。
3. **同函数缺少空格**：去掉逗号后 `THEN 3WHEN` 仍无分隔符。修复：WHEN 前补空格。

## 五、计数一致性验证（最终一致，零丢失）

修复后热点复测：100140 新增 550 点赞 → like_count +500（76,051→76,551）；新增 300 收藏 → favorite_count +300（4,274→4,574）；100172 评论持续追平关系表行数。

> 说明：点赞/收藏计数落库有延迟是因为 31.5 万条评论事件把事件管道堵住（relay 约 500 事件/秒），点赞事件排在队列里。最终全部落库、无丢失、无重复（事件级去重 + 增量计数器）。

## 六、故障恢复（Worker Kill/Restart）

压测中停止 worker 6 秒后重启：Redis 流中的待处理事件由 `XAutoClaim` 自动接管续传，计数无丢失、无重复（`cntdedup` 事件去重生效），重启后 Flusher 继续批量落库。

## 七、新瓶颈：事件管道吞吐

| 环节 | 吞吐上限 |
|---|---:|
| Outbox Relay（batch 100 / 200ms） | ~500 事件/秒 |
| Stream Consumer（batch 16） | 与 relay 同量级 |
| 评论洪峰（315K/90s） | ~3,500 事件/秒 |

写洪峰下 outbox 积压 30 万条、计数延迟数分钟。**这是第四轮暴露的下一个真实瓶颈**：需要 relay/consumer 批量放大（batch ×4-8）、Pipeline XADD，或评论/点赞事件降频（如评论计数改为合并窗口）。

## 九、结论与下一步

**第四轮成功标准全部达成**：200/300/500 并发错误率 <1%（实测 0%），行锁与连接等待显著下降，计数最终一致。

下一步（按收益）：
1. **事件管道扩容**：relay batch 100→500、consumer batch 16→64，XADD 走 Pipeline——直接解决写洪峰积压；
2. **减少互动 SQL**（方案 §10）：互动路径用 Note 缓存替代 `GetByID`，热点写 QPS 可从 ~2800 提升；
3. **flush 参数化**：Flush 间隔/批次做成配置，写密集场景调优。
